## 执行原则

1. 先只读盘点、查询和导出，不修改现有配置。
2. 优先使用系统提供的导出功能或只读 API；不得从页面截图推测缺失的配置内容。
3. 只有在系统没有导出功能时，才通过页面配置详情或只读接口逐项收集。
4. 不得将登录凭证、Cookie、Token、密码、个人敏感信息或无关业务数据写入导出文件。
5. 导出配置脚本时保留其原始文本和执行语义；不要擅自改写、清理或执行脚本。
6. 不要导出小区业务记录。只导出页面定义、组件、按钮及其配置和必要引用。
7. 遇到截图无法确认、页面没有展示或权限不足的内容，记录为“未确认”或“无法读取”，不要自行补值。
8. 迁移到另一套系统前，先进行预检查和差异报告；未经用户明确要求，不执行导入、覆盖、删除或权限变更。
9. 导入时必须先解析并校验整个文件。发现缺失依赖、同名冲突、代码字段冲突或版本不匹配时，停止写入并报告，不得部分导入。
10. 所有写操作应保持可追踪；如果目标系统支持事务或回滚，应使用并记录。

### F. 其他必要依赖

## 导出文件格式

生成一个 UTF-8 编码的 JSON 文件，文件名建议为：

`community-info-layout-export.json`

文件至少包含以下结构：

{
  "format": "layout-migration",
  "formatVersion": 1,
  "exportedAt": "<导出时间>",
  "sourceSystem": {
    "systemName": "<系统标识>",
    "baseUrl": "<脱敏后的系统地址>",
    "product": "<产品/租户信息，如可确认>",
    "applicationVersion": "<版本，如可确认>"
  },
  "scope": {
    "menuTitle": "小区信息",
    "parentMenuTitle": "建筑物",
    "includeBusinessRecords": false
  },
  "objects": {
    "menus": [],
    "layouts": [],
    "panels": [],
    "components": [],
    "buttons": [],
    "dataProviders": [],
    "apis": [],
    "workflows": [],
    "otherDependencies": [],
    "permissions": []
  },
  "relationships": [],
  "unresolvedDependencies": [],
  "warnings": [],
  "verification": {
    "allObjectsRead": false,
    "allReferencesResolved": false,
    "scriptsPreservedVerbatim": false,
    "businessRecordsExcluded": true
  }
}

要求：

- 只加入实际查到的字段和值；不适用或无法读取的字段要明确标注，不要编造。
- 配置脚本保留原文。若脚本内容过长，可放入同目录独立文件，并在 JSON 中写入相对路径、文件名和 SHA-256 校验值。
- 关系单独列出，至少包含 `from`、`relation`、`to`。
- 对系统生成的 ID、Code 做标记，区分“源系统标识”和“可迁移业务标识”；导入时不得默认复用目标系统的数据库主键。
- 导出前后计算文件校验值，并在报告中记录。
- 文件中不得包含小区列表等业务数据行。

## 导出后的检查

导出完成后逐项检查：

1. 菜单是否准确指向目标 Layout Code。
2. Layout 是否包含其 Panel，顺序是否完整。
3. 每个 Panel 是否包含全部组件和按钮。
4. 脚本和表达式是否完整保存，引用的 Code 是否已解析。
5. 是否错误包含业务数据、凭证或无关个人信息。
6. 是否存在未解析依赖、目标系统差异或版本限制。
7. JSON 是否可解析，SHA-256 是否与文件内容一致。

## 跨系统导入流程（仅在用户之后明确要求导入时执行）

1. 读取迁移文件并验证格式版本、文件校验值及必填字段。
2. 在目标系统进行只读预检查：核对产品版本、对象类型、引用依赖、同名对象和 Code 冲突。
3. 输出导入计划和差异清单。明确哪些对象会新建、复用或需要人工处理。
4. 如果存在无法安全解决的冲突、缺失依赖或版本不兼容，停止导入并说明原因。
5. 只有用户明确授权导入后，才创建或更新目标对象。
6. 按依赖顺序导入：基础依赖 → DataProvider/API/Workflow → 组件 → Panel → Layout → 菜单；权限只做报告，除非用户另行明确要求。
7. 建立目标系统新生成的 ID/Code 与源配置标识的映射，确保引用指向目标系统对象。
8. 导入后只读验证：检查菜单 URL、Layout、Panel、组件、按钮、脚本引用和显示顺序。
9. 输出结果报告：新建/复用/跳过的对象、标识映射、校验结果、未解决事项和回滚信息。
