---
name: code_analysis
description: 分析工作区代码的架构、入口、模块职责与调用链，并把完整报告写成 Markdown 文件。
when-to-use: 用户要求分析代码、梳理架构、追踪某功能怎么实现、看模块依赖、找入口、画调用链，或问某目录/符号是干什么的时候。不要用于单纯找 bug（用 code_review）或只做三句话项目简介（用 project_brief）。
---

分析过程只用 `list_files`、`grep_search`、`read_file` 和只读的 `agent(explore)`。不要改业务源码，不要调用 `edit_file`、`run_shell`。

最终交付物必须是工作区里的一个 `.md` 文件：用 `write_file` 写入完整报告。对话里只回复文件路径和一两句摘要，不要把整份报告贴到屏幕上。

权限：需要能写文件（`default` 或 `accept-edits`）。若当前是 `plan`，先说明无法落盘，请用户切换权限后再继续；不要只在对话里输出全文凑合。

先判断意图，再选重点（可组合，但一次报告只突出一个主问题）：

1. 全仓/目录概览：入口、目录职责、主链路
2. 功能追踪：某需求或接口从哪进、怎么走到哪
3. 符号/模块深挖：类或函数职责、谁引用、上下游
4. 变更影响：改某文件可能波及谁（用搜索近似，标明不确定）

步骤：

1. 定范围。用户给了路径、模块或符号就从那里开始；否则先 `read_file` `README.md`（没有再找同级说明），并用 `list_files` 摸顶层布局。禁止一上来无目标地通读全仓。
2. 找入口。按项目类型用 `list_files` / `grep_search` 定位候选，例如 `main`、`server`、`cli`、`app`、`__main__`、`package.json`、路由注册、导出符号。读到的入口才能写进结论。
3. 分片搜索。跨模块或范围大时，调用 `agent`，`agent_type` 用 `explore`，每次只查一个窄问题（例如「HTTP 入口在哪」「鉴权在哪」「谁调用了 X」）。不要指望一次 explore 扫完整个仓库。
4. 交叉验证。explore 或 grep 指出的路径，用 `read_file` 读关键片段后再下结论。没读过的文件、没看到的行号不要写进「证据」。
5. 定输出路径。用户指定了路径就用指定路径；否则写入 `exports/code_analysis.md`。若该文件已存在，先 `read_file` 再 `write_file` 覆盖；或按主题写为 `exports/code_analysis-<简短主题>.md`（文件名用英文小写、连字符，避免空格）。
6. 落盘。用 `write_file` 按下面模板写入完整 Markdown（简体中文）。没有依据的部分放进「未知与风险」，不要猜测冒充事实。
7. 回复用户。只给：报告路径、主结论一两句、如需可再深挖的一点。禁止把报告正文整段贴到对话里。

报告文件模板：

```markdown
# 代码分析：<主问题一句话>

## 结论
用 2～4 句话回答用户的主问题。

## 架构概览
- 入口：路径与如何启动/触发
- 核心模块：一张表或列表，每项为 `路径` | 职责 | 关键符号（仅列已读到的）

## 关键路径 / 调用链
由外到内编号列出；每一步尽量落到文件与符号。范围不够时写清停在哪一层。

## 证据
每条一行：`路径:行号` — 说明。没有行号的条目不要放这里。

## 未知与风险
未读到的部分、搜索近似带来的不确定、以及若继续深挖该优先看的文件。

## 下一步（可选）
可继续分析的点，或是否值得转 `code_review`。不要在本技能里直接改业务源码。
```
